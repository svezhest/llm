# DFlash2 на Qwen3.8-27B (5 бит): стыковка, 5-битное ядро, thinking, кэш промптов

10–11.11.2026, M1 Max 32 ГБ. План: `design/dflash2_27b_plan.md`. Цель `weights/qwen38-27b-mlx-5bit`, драфтер
`weights/qwen38-27b-dflash2`, `QWEN_KV_BITS=0` (путь А). Все сравнения скорости — внутри одного процесса с
чередованием вариантов. Разделы 1–3 сняты без поднятого лимита wired-памяти, разделы 4–7 — с
`iogpu.wired_limit_mb=28672` и `QWEN_WIRED_LIMIT_GB=27`.

Запуск: `QWEN_MODEL=weights/qwen38-27b-mlx-5bit QWEN_KV_BITS=0 QWEN_DRAFT=weights/qwen38-27b-dflash2 QWEN_MRQMM5=1
QWEN_WIRED_LIMIT_GB=27` (блок 8 выставляется сам, `QWEN_DRAFT_FP32` включается сам).

## Итог

- С новым 5-битным ядром (`QWEN_MRQMM5=1`) DFlash2 даёт ×1,77 на коде без thinking (13,3 → 23,4 tok/s) и ×1,41–1,44 с
  thinking (13,4 → 19,0–19,3 tok/s). Без ядра было ×0,81–1,10.
- В воркере драфтер не принимал ни одного черновика (0 из 420): приведение к fp16 переполняет его остаточный поток.
  Исправлено ручкой `QWEN_DRAFT_FP32` (авто для DFlash2): 4-битные веса, активации fp32.
- С ядром вывод не равен обычному жадному побитно: совпало 15 из 16 ответов без thinking и 12 из 16 с thinking; четыре
  расхождения из пяти — в точках, где зазор между первым и вторым логитом ≤ 0,016, одно — при зазоре 0,25.
- Бюджет thinking больше не выключает драфтер: на 27B 8 из 8 ответов равны обычному циклу с тем же бюджетом.
- Кэш промптов с драфтером работает: попадание даёт TTFT 0,1–5 с вместо 26–36 с, вывод равен холодному.
  После доработки 2026-11-11 (раздел 7) запись кэша хранит контекст драфтера: точный повтор и следующий ход
  принимают черновики как холодный прогон (было на 5–20 % меньше на повторе); KV ответа и отмена prefill
  поддержаны и для строк с драфтером (следующий ход без thinking: TTFT 0,75–0,9 с вместо 31–36 с).
- Точное ядро проверки mlx-vlm на 5 битах при блоке 8 стоит 1,6 с на раунд — непригодно.
- Длинный контекст (раздел 8): с одной копией KV (`QWEN_PROMPT_CACHE_MOVE=1`) диалог на 60K токенов идёт с кэшем:
  холодный prefill 515–521 с, следующие ходы — TTFT 0,9–2,1 с; 11,5–12,7 tok/s с thinking, 14,3–16,0 без (обычный
  декодинг там 9,6); пик 26,4 ГиБ при лимите 27.

### Переполнение fp16

`QWEN_FP16=1` приводил драфтер к fp16. У этого драфтера остаточный поток после первого слоя достигает 5,69·10⁴
(предел fp16 — 65 504), на следующих слоях переполняется, после финальной нормы все значения NaN, все логиты NaN.
В bf16 то же самое работает, потому что сумма fp16-эмбеддинга и bf16-весов повышается до fp32. Трасса по стадиям:
`scripts/perf/dflash2/draft_overflow.py`.

Исправление в `worker.py`: `_draft_wide` / `_widen_drafter`. Веса квантуются как раньше, оставшиеся bf16-параметры
(масштабы и смещения квантования, нормы, ядра свёрток) переводятся в fp32, кодовые книги селектора — в fp16, входные
эмбеддинги блока и скрытые состояния цели приводятся к fp32, выход драфтера перед `lm_head` цели — к типу цели.
Драфтер 9B не затронут. Если за запрос не принят ни один из ≥ 64 черновиков, в лог идёт предупреждение.

Доля принятых и цена блока (`draft_wide.py`, 5 задач кода × 96 токенов, thinking выключен, принудительное
следование жадному ответу цели, пробы через 3 позиции):

| Драфтер | Принято из 7 (блок 8) | Принято из 4 (блок 5) |
|---|---|---|
| bf16, без квантования | 3,28 | 2,50 |
| 8 бит, fp32 | 3,28 | 2,51 |
| 5 бит, fp32 | 3,41 | 2,57 |
| 4 бита, fp32 | 3,16 | 2,43 |
| любой в fp16 | 0 | 0 |

Блок драфтера (4 бита, блок 8, 5 новых строк контекста, один `eval`; `draft_prof.py`): 36 мс в fp32, 32 мс в fp16
(разные процессы). По стадиям с синхронизацией после каждой: MLP 15,5 мс, `lm_head` цели на 7 строках 11,8 мс,
внимание 6,3 мс, свёртки 8,9 мс, селектор 2,6 мс. Без квантования (bf16) блок стоит ~350 мс. Память драфтера:
1,7 ГБ в 4 битах.

## 4. 5-битное ядро (`QWEN_MRQMM5`)

`mrqmm.py` обобщён по разрядности: общий исходник и «весовая сторона» для 8, 5 и 4 бит (4 — только для замера).
8-битный путь не изменился (исходник ядра при 8 битах зафиксирован тестом по sha256, выход побитно равен прежнему).
Ручка `QWEN_MRQMM5=1`, по умолчанию выключена; при выключенной 5-битные модели идут как раньше.

## 6. Драфтер с бюджетом thinking

Раньше запрос с `thinking_budget` шёл обычным циклом. Теперь (`_Scheduler._spec`, `_budget_cut`): критерий бюджета
видит каждый выданный токен; блок раунда обрезается на токене, после которого бюджет навязывает следующий (остальные
черновики уходят из кэша при фиксации раунда); навязанные `\n</think>` выдаются и подаются обычными шагами, их
скрытые состояния идут драфтеру как контекст.

- CPU: `tests/test_scheduler.py::test_dflash_thinking_budget` — 13 сочетаний бюджета и `max_tokens`, два вида
  черновиков (граница внутри принятого блока и на собственном токене цели), вывод равен обычному циклу.
- 27B, бюджет 48, 8 задач, 160 токенов (`raw/ab27_budget48_ident.*`): 8/8 через точную проверку (блок 5) и 8/8
  через ядро (блок 8).

### Доработка 2026-11-11

1. **Контекст драфтера в записи кэша.** Каждое состояние, которое сохраняет строка с драфтером (контрольные точки,
   конец записи, префикс отменённого prefill, конец ответа), несёт скрытые состояния целевой модели для последних
   позиций перед ним (слои драфтера; на 27B 51 КиБ на позицию). Строка, возобновившаяся с такого состояния,
   отдаёт их драфтеру вместе с тем, что досчитала сама.
   - `QWEN_DRAFT_TAIL` (128) — длина для контрольных точек, 6,6 МБ на состояние.
   - `QWEN_DRAFT_TAIL_END` (2048, не больше окна драфтера) — длина для конца записи, до 105 МБ на запись.
   - Контрольная точка внутри окна конца записи (начала последних сообщений) берёт контекст из хвоста конца:
     `_resume_tail`, без дополнительной памяти.
   - Хвост хранится лишним элементом состояния (`_with_tail`), поэтому наследуется, поглощается, прореживается,
     учитывается в байтах записи и пишется на дисковый уровень вместе с состоянием.
2. **KV ответа** (`QWEN_PROMPT_CACHE_REPLY`) теперь сохраняется и для строк с драфтером, в том числе переведённых
   в батч посреди ответа. Не сохраняется, если стоп-токен оказался среди принятых черновиков и за ним приняты ещё
   черновики (кэш ушёл дальше стопа), и, как прежде, для ответов с рассуждением.
3. **Отмена во время prefill** строки с драфтером сохраняет досчитанный префикс, как у обычной строки.
4. **Ошибка в окне контекста при prefill** (была и на 9B): из списка слэбов выбрасывался старший, пока все, кроме
   *новейшего*, покрывали окно; короткий последний слэб после полного оставлял драфтеру только себя (слэбы
   2048 + 2048 + 40 → 40 позиций). Теперь окно покрывается всегда.

  52 раунда вместо 38 (декодирование на 27 % медленнее холодного). С хвостом длиной в окно раунды совпадают с
  холодными. Отсюда отдельная длина для конца записи.
- Вывод равен холодному во всех 12 парах этих двух прогонов (и во всех 30 парах после доработки), хотя попадание через KV ответа не обязано быть побитно равным (класс
  численности батч-декодинга).

Thinking включён, короткое продолжение (`raw/cache_hit_think_short.*`): ответ с рассуждением не сохраняется,
следующий ход возобновляется с контрольной точки в начале последнего сообщения хода 1 и берёт контекст драфтера
из хвоста конца записи.

|---|---|---|---|---|---|
| ход 1, точный повтор | 1 | 0,09 | 52 / 65 / 60 | 2,67 / 1,94 / 2,20 | равен холодному, 3/3 |

Принятые длины совпадают с холодными в каждом раунде.

Память: запись на 3,9K токенов выросла с 716 до 835 МБ (хвост конца 105 МБ + два по 6,6 МБ); состояние GDN на 27B —
154 МБ. Пик процесса с кэшем из четырёх записей (3,0 ГБ) 26,3–26,7 ГБ = 24,5–24,9 ГиБ при лимите 27 ГиБ (до
доработки 25,7 ГБ): запас около 2 ГиБ. Промпты в замере — до 4,3K токенов; длинный контекст с fp16 KV не мерялся.
По учёту воркера (расчёт, не замер): под строки и кэш вместе есть бюджет KV 3,24 ГиБ + резерв prefill 3,4 ГиБ =
6,64 ГиБ, а KV в fp16 — 64 КиБ на токен и лежит дважды (строка + запись кэша, `store` копирует). Запись на L токенов
остаётся, пока 2 × L × 64 КиБ + ~1,4 ГиБ (состояния, резерв генерации, GDN строки) ≤ 6,64 ГиБ, то есть до
L ≈ 40K; длиннее — «not kept», каждый ход холодный. Для 64K с кэшем нужно ~9,4 ГиБ, то есть лимит ~30 ГиБ из 32.

Что остаётся неподдержанным для строк с драфтером: квантованный KV (драфтер выключается при `QWEN_KV_BITS` ≠ 0).
Состояния, сохранённые обычной строкой (батч, сэмплирование, грамматика), хвоста не несут: драфтер после такого
попадания стартует с досчитанных позиций, как раньше. Дисковый уровень с драфтером проверен только тестом на
малой модели (хвост переживает выгрузку и загрузку), на 27B не гонялся.

## 8. Длинный контекст: одна копия KV (2026-11-11)

Цель — диалог на 64K с драфтером и кэшем в один поток. С копиями запись кэша длиннее ~40K не оставалась (раздел 7).

**Режим `QWEN_PROMPT_CACHE_MOVE=1`** (только `QWEN_MAX_BATCH=1`, fp16 KV, без дискового уровня). Попадание в запись
своего диалога переносит её буферы в строку (запись на это время уходит из кэша), в конце prefill ничего не копируется,
в конце строки её собственные буферы становятся записью (промпт и поверх тех же буферов — ответ). Ответы, число
переиспользованных токенов и содержимое кэша те же, что с копиями (`tests/test_pcache_move.py`: каждый сценарий
проигрывается обоими способами). Описание и ограничения — README, «One KV copy for a single stream».

**Что мешало на 60K** (первые два прогона упали с `Insufficient Memory`, второй перед этим шёл 0,57 tok/s):
