test_sample_rows_topk_fast_full_vocab` (Metal, V = 248320). GPU-скрипты: `scripts/perf/sampler_topk/`.

## Что сделано

Сейчас `_Sampler.filtered` на (rows, 248320) делает так: `x / temp` → min_p через softmax по V →
`mx.topk` (на Metal это полная сортировка, так устроен argpartition MLX) → `argsort` по V →
softmax + cumsum по V → `put_along_axis`. Потом `categorical` по V (Gumbel на 248K). Карточный
сэмплер при B = 16 стоит 7.8 мс GPU (групповой путь).

С `QWEN_SAMPLER_TOPK_FAST=1` и `0 < top_k < V` (`_Sampler.survivors`) порядок такой:
1. `order = argsort(x)` (одна стабильная сортировка по V), `ids = order[V−k:]`, `xs = x[ids]` по
   возрастанию; `kth = xs[0]` (= `topk(x, k).min()`), максимум = `xs[−1]`;
2. min_p внутри k: `exp(xs − max) ≥ min_p`;
3. **ничьи на k-й позиции.** `filtered` держит все токены со значением `kth`, их может быть
   больше k. `n = #(x ≥ kth)` по V (одна поэлементная редукция), лишних `extra = n − k`; это
   позиции `[V − n, V − k)` отсортированного `order`. При `kth = −inf` (конечных логитов < k:
   маска грамматики) `extra = 0`: у этих «ничьих» нулевая масса;
4. top_p по выжившим в возрастающем стабильном порядке (лишние ничьи первыми). Неотсортированная
   масса w = exp(x − max). Из лишних уходят первые `floor(thr·Z / w_kth)` (с наименьшими
   индексами), из k — те, у кого `base + cumsum(w) ≤ thr` (thr = (1 − top_p)·Z). Верхний не
   уходит никогда;
5. draw: `categorical` по k + 1 логитам: k кандидатов плюс «корзина» лишних ничьих с логитом
   `kth + log(count)`. Если выпала корзина — равномерно один из оставшихся (`uniform` по своему
   ключу). Ключ строки делится на два (`split`), seed воспроизводим.

Групповой путь `sample_rows` / `_sample_group` вызывает `s0.prepare(stack)` один раз на стек и
`s.draw(x[j:j+1])` на строку: `_TopK` режется по строкам как массив, у каждой строки свой ключ.
Greedy, `top_k = 0` и `top_k ≥ V` идут прежним путём (`prepare` → `filtered`). DFlash `pick`,
guide (`sample(logits, sampler)`) и B = 1 (`_sample`) идут через `__call__` → `prepare`, так что
быстрый путь получают все.

## Почему распределение то же (порядок vLLM: penalties → temperature → min_p → top_k → top_p)

* Penalties и temperature не трогаются (`_Penalties` до сэмплера; `x = logits.f32 / temp`, как в
  `filtered`).
* **min_p считается относительно максимума**, а он всегда в top-k: `p_i < p_max·min_p ⇔
  exp(x_i − x_max) < min_p`, нормировка сокращается. min_p и top_k оставляют верхние множества
  значений, поэтому их композиция в любом порядке = пересечение. Если min_p оставил меньше k
  токенов, то в `filtered` kth = −inf и top_k ничего не режет; здесь те же токены отсекает сама
  маска min_p. Все выжившие лежат в k наибольших плюс ничьи с k-м.
* **top_p**: `filtered` сортирует по возрастанию (MLX argsort стабилен: проверено на CPU и Metal,
  ничьи по индексу) и выбрасывает префикс, где кумулятивная масса ≤ 1 − top_p. У отсечённых −inf
  масса 0, поэтому кумулянта нужна только по выжившим, а это k кандидатов плюс лишние ничьи
  (их кумулянта j·w_kth). Нормировка внутри k эквивалентна: Z тот же (те же ненулевые
  слагаемые), сравнение c ≤ thr·Z ⇔ c/Z ≤ thr.
* **Ничьи** обрабатываются как сейчас: на k-й позиции выживают все (корзина); top_p внутри группы
  ничьих режет с младших индексов (как стабильный argsort `filtered`); ничьи с максимумом
  остаются в k.
* **Отличие — только округление.** softmax/cumsum по k членам вместо V дают другой порядок
  суммирования тех же слагаемых. Токен ровно на границе min_p / top_p (~1e-7 отн.) может
  оказаться по другую сторону; в тесте такой случай есть (50 равных максимумов при top_p 0.5:
  25/50 = 0.5 в точной арифметике). Поток случайных чисел другой (k + 1 значений плюс uniform
  вместо V Гумбелей), поэтому при данном seed токены другие. Отсюда ручка, по умолчанию 0.

## Инварианты (самопроверка)

* Ручка off: `_Sampler.fast = False` → `prepare` = `filtered`, `draw` от массива = прежний
  `split` + `categorical`; `_sample_group` вызывает `prepare` вместо `filtered` (то же самое).
  Тест `test_off_is_the_old_path` воспроизводит поток ключей вручную. Существующие
  `test_sample_rows_*` проходят, в том числе `b[1].filtered = boom` (prepare зовёт атрибут
  экземпляра).
* MLX: только на потоке планировщика, никакой синхронизации; все размеры статичны (k, V). Нет
  `.item()`, ветвление только по Python-параметрам.
* Память: `order` (rows × V uint32) живёт до draw: при B = 16 это 16 МБ, как argsort в `filtered`.

## Тесты (CPU, `tests/test_sampler_topk.py`, 27 тестов, < 1 с)

* Полное распределение, которое рисует `_TopK` (k кандидатов плюс корзина, размазанная по своим
  токенам), сравнивается с `softmax(filtered(x))`: тот же носитель и вероятности до fp32
  (atol 2e-6, rtol 1e-5).
  * 7 конфигов (карта, top_k only, min_p, top_p 0.5, все три, top_k 1, top_k 511) × fp16/fp32,
    случайные логиты.
  * Ничьи: 3/40/200 токенов на k-м значении вне k, 50 равных максимумов, полностью плоская
    строка, 64 равных топ-логита, блок ничьих у среза.
  * top_p режет группу ничьих внутри и вне k: оставлены ровно {50, 60}.
  * −inf: маски, конечных меньше k, 3 равных конечных.
* Строки, где токен лежит ровно на границе (float64-эталон порядка vLLM, `boundary`), проверяются
  только на носитель вне граничных токенов. Среди случайных строк таких 1 из 168.
* Частоты 40000 вытягиваний совпадают с распределением (atol 0.012), лишние ничьи тянутся тоже;
  seed воспроизводим, другой seed даёт другое.
* Ручка off бит-в-бит; быстрый путь только при top_k > 0 и < V; greedy не тронут.
* `sample_rows` с ручкой on: групповой draw == каждая строка отдельно (5 шагов, смешанные
  конфиги, ничьи).
* Metal (V = 248320, 16 строк, 4 конфига, ничьи / плато / равные максимумы): распределение ==
  `filtered`, стек == строка бит-в-бит (все массивы `_TopK` и токены). Проходит.

## GPU-план

Команда (одна, ~10 мин, пик ~11 GB с моделью, без неё < 0.5 GB):

```zsh
zsh scripts/perf/sampler_topk/run.zsh         # E2E=0 — без модели; вывод: $PERF_OUT/sampler_topk/
```

1. Metal-корректность на 248K (`-k sample_rows`).
2. `sampler_ab.py`, без модели: логиты (B, 248320) fp16. Продакшн-входы (B = 1 — сэмплер строки;
   B ≥ 2 — `sample_rows`, одна группа). Конфиги: card (0.6/0.95/20), card-think (1.0/0.95/20),
   topk50, card+min_p 0.05. B = 1/4/8/16. off/on чередуются ABBA в одном процессе, 40 повторов,
   медиана мс на шаг. Плюс куски старого пути (topk, argsort, argpartition, categorical при
   B = 16).
3. `e2e_ab.py`, настоящая 9B (`QWEN_KV_BITS=0`, без драфтера, `QWEN_BATCH_PREFILL_SHARE=1`):
   16 одновременных запросов card с seed, `ignore_eos`, 256 токенов; раунды off/on/on/off ×2.
   Метрики: медиана ток/с на запрос, шаг (мс), агрегат за окно, когда декодят все.
4. Ожидание: card B = 16 7.8 мс → ~3–4.5 мс (одна сортировка вместо двух, без scatter и без
   V-широких softmax/cumsum/Гумбеля), B = 1 — порядка −40 %; шаг e2e при B = 16 ~52 мс → −3–4 мс
   (−5–8 %).
5. **Pass / fail**: pass, если card при B = 16 on ≤ 0.75 × off, e2e-шаг on ≤ off (медианы ABBA)
   и Metal-тест прошёл. Если on ≥ off при B = 1, разбирать (может, `argsort` с индексами дороже
   value-`topk`); если e2e не показал выигрыша при выигрыше в microbench, значит сэмплер не на
   критическом пути (step-ahead), и это фиксируем.
